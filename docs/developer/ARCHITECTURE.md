# Project architecture

Where things live in this codebase and what each piece is responsible for.
For what the app *does* and how to run it, see the main
[README.md](../../README.md); for documentation on specific load models, see
the [model overview](../user/model_overview.md), which compares every model and
links to each one's page and developer reference.

## Terminology

- **Multi-stage trip table** - PERC1's 4-stage stepped voltage trip table
  (`VDPA`/`DMA` plus `VDPA1-3`/`DMA1-3` for undervoltage, `VDUA`/`TDUA` plus
  `VDUA1-3`/`TDUA1-3` for overvoltage). The PERC1 vendor manual calls this
  **"Option 3"**; prose that quotes the manual keeps that name, but code,
  file and test names use `multistage`. See
  [PERC1_MODEL.md](PERC1_MODEL.md#option-3-is-always-live).

## Package layering

`src/` is organised so a reader can find a piece by what it is for, and so imports only point down this list
(each package may import the ones above it):

```text
load_models   the models: CONs, .dyr records, simulators        (imports nothing else)
presets       the ride-through preset library and its envelope geometry
editor        what a block edits: field specs, rows, edit tracking, .dyr import
preview       what a block's response looks like: simulation -> verdict, charts, pages
export        what the app writes: the .dyr file and the HTML report
ui            the PySide6 widgets (nothing here computes a result)
app           plumbing: launcher, settings, resources, config, tokens
psse, blackbox, dev    PSS/E runner contract, black-box model testing, the automation CLI
```

`tests/test_layering.py` holds the exact table and fails on a module-level import against it. Imports inside a
function are the documented exceptions: `load_models` reaches `preview` for a model's report figure, `app/launcher.py`
opens the `ui`, and the black-box and CLI features reach each other lazily. `dev/` (the `perc-studio` CLI and the
advanced model validation) is imported by nothing in the desktop app, so the installer does not need it. Shared code goes in the lowest package that can
hold it: the helpers the PERC models share are `load_models/common.py`, envelope geometry is `presets/envelope.py`,
and what the response pages share is `preview/style.py` and `preview/frame.py`.

## Module responsibilities

- `src/main.py`
  - Script entry point for the desktop application (`python src/main.py`);
    delegates straight to `app.launcher.main()`.

- `src/app/launcher.py`
  - The `perc-studio` console entry point. With no arguments or only options it
    parses `--mode {screening,post-commissioning}` (default `screening`) and
    launches the PySide6 `MainWindow` on that tab. When the first argument is a
    command (`params`, `export`, `sweep`, ...) it hands the arguments to the
    automation CLI (`dev.cli.main`), imported inside the function so the desktop
    app never loads it; `help` shows the CLI's command list.

- `src/ui/main_window.py`
  - The PySide6 desktop UI: `MainWindow` on the `ui.shell.AppShell` (app bar
    with the workflow tabs, closable run tabs and the version pill), with the
    Screening and Post-Commissioning pages and the Documentation tab
    (`ui.docs.DocumentationPanel`). Each model block (Screening, IT/UPS, VFD)
    is a `ui.block.BlockController` that owns its model bar, parameter rows
    (`editor.parameter_rows`), edit tracker (`editor.block_state`), test-event card and live
    preview (`preview.model` + `preview.page`); `MainWindow`'s older per-block
    names (`pc_it_fields`, `_apply_preset_to_block`, ...) delegate to it.
    Colours and sizes come from `app/tokens.py`. Builds its own
    session-state dictionaries directly from form widgets and calls into
    `load_models/`/`export/dyr.py`/`export/report.py` for derivation and export. Each IT/VFD/Screening
    block has a **PERC1 model version** selector (DLL or standard); the parameter
    rows are rebuilt from that model's `editor.model_ui.ModelUiSpec`. A
    Post-Commissioning block can also hold a user-defined model, taken unedited from the
    user's own `.dyr` (`editor/user_model.py`). Other models (CLOD aside) are not in the UI - see
    [ADDING_A_LOAD_MODEL.md](ADDING_A_LOAD_MODEL.md#what-stays-perc1clod-specific).

- `src/load_models/`
  - The registry of PSS/E dynamic load models (`LOAD_MODELS`). Each model is
    a `LoadModel` (`base.py`) - its CON names and defaults, `.dyr` writer,
    and optional parser, analytic simulator, preset encoder and report
    figure. Everything in the developer loop dispatches through a block's
    `model_id`, so **adding a model means adding one subpackage and one
    registry line** - see [ADDING_A_LOAD_MODEL.md](ADDING_A_LOAD_MODEL.md).
  - `perc1_dll/` - the engineering core for PERC1: `cons.py` (the 173-CON
    layout, vendor defaults, `PERC1_DEFAULT_CONS`, display fields,
    `voltage_stage_cons`, `ZIP_EXPONENT_MAP`), `dyr.py` (the `PERCBL` writer and its
    inverse parser), and `simulation.py` (`simulate_perc1_response` and
    `simulate_perc1_frequency_response`, the analytic voltage- and
    frequency-event responses behind the live chart and the mock runner).
  - `perc1_standard/` - the PSS/E 36.7 built-in `PERCxx1U` model: `cons.py` (30
    CONs, `CON_SPECS` limits, `validate_cons`), `dyr.py` (the `MAINxx10` +
    `PERCxx1U` writer and parser), `presets.py` (ride-through preset to its
    single cease/reconnect cycle) and `simulation.py` (analytic response behind the
    mock runner and the live chart; checked against the PSS/E traces). The evidence
    is in the PSS/E validation library (not published).
  - `perc2_standard/` - the PSS/E 36.7 built-in `PERCxx2U` model: `cons.py` (6
    flags + 57 CONs, `CON_SPECS` with the measured notes, `validate_cons`,
    `effective_limits`), `dyr.py` (the `MAINxx10` + `PERCxx2U` writer and parser),
    `presets.py` (a preset's PERC1 DLL bundle onto the momentary, long and
    frequency checks) and `simulation.py` (the cease/reconnect state machine as
    PSS/E 36.7.1 runs it, PSS/E's point-3 defect included). The evidence is in
    the PSS/E validation library (not published); the reference is
    `docs/developer/PERC2_MODEL.md`.
  - `perc2_dll/` - the ISO-NE PERC2 v2.3 user model (`PERC2_v3x_v2p3.dll`,
    `PERCBL` with 179 CONs: the PERC1 DLL plus a Q lead-lag and momentary
    cessation's own reconnect band and ramps): `cons.py` (2 ICONs + 179 CONs,
    `validate_cons` with the measured hazards, `ramp_seconds` - RAMPA/RAMPUA x
    LFM), `dyr.py` (writer and parser on top of the PERC1 DLL's, routed by the
    header's CON count through `LoadModel.matches_dyr`), `presets.py` (a preset's
    PERC1 DLL bundle with RAMPA/RAMPUA / LFM and VRPA capped at 0.95) and
    `simulation.py` (the PERC1 DLL simulator plus momentary cessation). The
    evidence is in the PSS/E validation library (not published); the reference is
    `docs/developer/PERC2_DLL_MODEL.md`.
  - `clod/` - CLOD's composition fields, `derive_clod_params` (facility
    archetype → composition) and `.dyr` writer. Export-only.

- `src/presets/ridethrough.py`
  - The explicit, self-contained utility/RTO/ISO ride-through preset
    library - a single `RIDE_THROUGH_PRESETS` dict keyed by preset id, each
    value a `RideThroughPreset` dataclass instance (ERCOT, SPP, PJM, MISO,
    both NERC entries, plus three generic tiers). **This is the one file to
    edit to add or change a preset** - no other module needs to change; new
    entries appear in the UI dropdown and the in-app Documentation tab
    automatically. See
    [ADDING_A_PRESET.md](ADDING_A_PRESET.md) for the step-by-step guide;
    [docs/user/presets/](../user/presets/README.md) is the user-facing companion.

- `src/export/`
  - `dyr.py` assembles the desktop app's full `.dyr` file (`build_dyr_text`,
    from the per-model record writers in
    `load_models/`) and resolves each block's parameters (`get_it_params`, ...).
  - `report.py` builds the HTML review report (`build_html_report`) and embeds
    each block's response page from `preview/`.

- `src/preview/`
  - What a block's response looks like, without Qt. `model.py` runs one
    simulation and derives the verdict, figures and timeline; `page.py` is the
    live preview in the window. The report's 2x2 Plotly page is `perc1_dll.py`
    (`build_perc1_response_figure`, `render_perc1_response_page`) for the PERC1 DLL,
    and `frame.py` for the standard-style models: a `ResponsePage` holds the
    shared figure layout, page assembly and live update once, and `standard.py`
    and `perc2.py` each supply only their model's panels. `perc2_dll.py` reuses
    the PERC1 DLL page through the v2.3 simulator. `style.py` is the plot palette
    and small helpers all of them share.

- `src/app/config.py`
  - Shared defaults (`DEFAULTS`), branding colors (`CURENT_GREEN` family,
    `TVA_NAVY`), packaged logo asset paths (`CURENT_LOGO_PATH`,
    `CURENT_ICON_PATH`, `TVA_LOGO_PATH`).

- `assets/branding/`
  - The real CURENT and TVA logo files used in the app header/footer and the
    HTML report header/footer, plus `SOURCES.md` documenting where each was
    obtained and its license/trademark status.

- `src/dev/validation/case_model.py`
  - The canonical, JSON-serializable `LoadCase` parameterization object
    used by the `perc-studio` CLI and by scripts/agents that need a
    programmatic entry point instead of the GUI. Each of its `it`/`vfd`/
    `motor` blocks is a `ModelBlock` naming its load model (`model_id`).
    Construction paths `case_from_preset`,
    `case_from_model_defaults` and `case_with_overrides`, model-aware
    `block_dyr_record`/`schema_problems`,
    plus `case_to_ui_state`/`ui_state_to_case` converters to/from `ui/main_window.py`'s
    own flat state dict shape (not adopted by `ui/main_window.py` itself - see
    `src/dev/cli/README.md`).

- `src/psse/runner.py`
  - The `PsseRunner` interface (`FaultScenario`, `SimulationResult`,
    `PsseRunner` protocol, `get_runner()`) that both `MockPsseRunner` and the
    real PSS/E runner (`blackbox.runner.PsseSubprocessRunner`, once a PSS/E
    install is selected) implement identically. The mock runner finds the record's load model from the
    `.dyr` text and runs that model's own parser and `simulate` hook - see
    `src/dev/cli/README.md`'s "PsseRunner contract" section.

- `src/dev/validation/checks.py`
  - Compares a `SimulationResult` against what a `RideThroughPreset`'s own
    envelope says should happen (`expected_trip_for_scenario`,
    `validate_result`, `validate_case`), reusing `presets/envelope.py`'s pure
    envelope-geometry helpers. Also has `evaluate_multistage_probe`, which
    answered whether the compiled DLL always evaluates Option 3's stepped
    trip table (it does;
    see `docs/developer/PERC1_MODEL.md`'s "Option 3 is always live") and now serves as
    a permanent regression guard against that finding.

- `src/dev/validation/sweep.py`
  - Loads a sweep spec (JSON/YAML) and drives the generate -> export ->
    run -> validate -> report loop across a cartesian product of presets x
    fault scenarios (`run_sweep`) - the engine behind `perc-studio sweep`. The
    spec's optional `"model"` key picks the load model under test.

- `src/blackbox/` and `src/psse_worker/`
  - Black-box validation (how it works and its known limits:
    [BLACK_BOX_VALIDATION.md](../black_box/BLACK_BOX_VALIDATION.md)): a load
    model's `.dyr` records (and DLLs) run unchanged on a one-bus PLBVF1 rig in
    the user's own PSS/E, and the protocol characterizes the model as a whole
    and compares it with the presets. Nothing in the app imports `psspy`:
    `psse_worker.py` runs under the Python of the chosen PSS/E install, one
    process per case, started by `supervisor.py`. `protocol.Validation` runs
    the stages; `search.BoundarySearch` finds where the outcome changes along a
    disturbance axis; `classify` reads the outcome from P alone; `report`
    writes the HTML/JSON/bundle. `runner.PsseSubprocessRunner` is the real
    `PsseRunner`. The Black-Box Validation tab (`ui/blackbox/tab.py`) and
    `perc-studio psse check` / `perc-studio blackbox` are the front ends.
    `packaging/perc_studio.spec` ships `psse_worker.py` and `outx.py` as data files, since they run as scripts.
    `outx` reads PSS/E's channel output file without PSS/E; `explorer` lists a
    run's cases and builds the plot figure, and `ui/blackbox/explorer.py` is its widget
    (pick tests and channels, interactive plot). `runs` summarizes run folders from their
    `validation.json`; `tolerance` builds the tolerance curve and its comparison with a
    standard; `ui/blackbox/runs.py` shows a run's summary and its own tab.
    Tests run against a fake `psspy` in `tests/fixtures/fake_psse/`.

- `src/dev/validation/reports.py`
  - HTML/JSON report builders for the `perc-studio` validation loop
    (`build_case_report_html`, `build_sweep_summary_html/json`). Kept
    separate from `export/report.py`: this is CLI-specific output, not part of
    the live app's GUI export path.

- `src/dev/cli/`
  - The automation CLI itself (Click), run as `perc-studio <command>`: `app.launcher.main` hands it any
    invocation whose first argument is a command. It requires no PySide6/Qt runtime. One module per command group (`params.py`, `pipeline.py` for
    export/run/validate/report/sweep, `presets_cmd.py`, `dyr_cmd.py`, `scenario_cmd.py`, `blackbox_cmd.py`,
    `results_cmd.py`), all printing the envelope from `_output.py`. See
    [src/dev/cli/README.md](../../src/dev/cli/README.md) for the command map and the reference pages under
    `src/dev/cli/docs/`.

- `utils/scripts/generate_envelope_figures.py` / `utils/scripts/generate_parameter_preset_figures.py`
  (repo root, source checkout only; `packaging/build_release.py` refuses to bundle `utils/`)
  - Regenerate the SVGs in `docs/user/figures/` - the per-preset voltage-envelope and frequency-deadband
    charts embedded in `docs/user/presets/` and the generic-tier
    comparison charts embedded in `docs/user/parameter_tiers.md` - directly from
    `RIDE_THROUGH_PRESETS`, reusing the same geometry helpers the live app's
    Plotly panel uses. Run after changing a preset's envelope or CON bundle.
    The PNGs in `docs/user/figures/` are frozen PSS/E results from the PSS/E validation library (not published) and are not
    regenerated here.

- `tests/fixtures/multistage_trip/`
  - A pair of `.dyr` files identical except for their multi-stage trip
    table values: `ercot_nogrr282_vendor_default_stages.dyr` (stages 2-4
    left at the vendor-sample defaults, as the app exported before
    2026-09-24) and `ercot_nogrr282_full_curve_stages.dyr` (the preset's real
    curve encoded into stages 2-4). They answered whether the compiled PERC1
    DLL always evaluates Option 3's stepped trip table (it does) - kept as a
    permanent, real-DLL-validated regression fixture, not just historical.
    The PSS/E runs against them are in the PSS/E validation library (not published).

- `tests/`
  - Each `test_<module>.py` covers the `src/<module>.py` of the same name
    (`test_cli.py` covers `src/dev/cli/`).
    `test_multistage_trip_regression.py` is the one cross-module test: it
    pins the PSS/E-confirmed finding that every stage of the multi-stage
    trip table is evaluated, using `tests/fixtures/multistage_trip/`.
